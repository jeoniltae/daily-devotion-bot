# 코딩 가이드라인

프로젝트 배경·아키텍처·제약은 [CLAUDE.md](../CLAUDE.md) 참고.
코드는 성격이 다른 두 덩어리로 나뉘므로 규칙도 분리한다.

- **발송 스크립트** — GitHub Actions에서 무인 실행되는 headless Node/TypeScript. 현재 유일한 산출물.
- **대시보드** — 3단계 선택 항목. 아직 만들지 않았고 프레임워크도 미확정.

---

## 하지 말아야 할 것

### 공통 (모든 코드)

- `any` 타입 사용 금지.
- `default export` 금지 → Named export 사용.
  - 예외: 프레임워크가 default export를 강제하는 파일(`page.tsx`, `layout.tsx`, `route.ts`, `*.config.ts` 등).
- 토큰·서비스 계정 키 등 자격증명을 코드에 하드코딩 금지 → `process.env`로 주입받는다. (CLAUDE.md 8장)
- 자격증명이나 `process.env` 전체를 로그로 출력 금지. **Actions 로그에 한 번 남으면 회수할 수 없다.**
- 디버깅용 잔여 `console.log` 커밋 금지. (의도적 운영 로그는 예외 — 아래 참고)
- 서버 로컬 시간대에 의존 금지. cron은 UTC, `sentAt`은 KST로 각각 명시해 계산한다. (CLAUDE.md 6장)
- 요청 범위 밖의 기존 파일 수정 금지 — 지침은 신규 파일 또는 직접 수정 요청된 파일에만 적용.

### 발송 스크립트

- **프로덕션 텔레그램 채널로 시험 발송 금지.** 공개 채널은 발송 즉시 영구 아카이브로 누적되고 포워딩으로 퍼져 되돌릴 수 없다. 테스트는 별도 테스트 채널 또는 dry-run 모드로만 한다. (CLAUDE.md 9장)
- **성경 본문(`verseText`) 임의 수정 금지.** 개역개정 원문 그대로 전달한다. 표기·띄어쓰기를 오타로 판단해 교정하거나 문장을 다듬지 않는다. 저작인격권 문제다. (CLAUDE.md 9장)
- **성경 저작권 표시 문구 임의 제거·축약 금지.** 개역개정은 대한성서공회의 저작권물이며 표시 문구는 이용 허락의 **조건**이다. 메시지가 길다는 이유로 생략하거나, 빈 값 생략 로직(`title`·`source` 등)에 함께 묶어 처리하지 않는다. (CLAUDE.md 9장)
- **빈 컬럼에 죽는 코드 금지.** `title`·`verseRef`·`verseText`·`source`가 비는 것은 예외 상황이 아니라 **예상되는 정상 입력**이다. 아래 "단순함 우선"의 "불가능한 시나리오 에러 처리 금지"는 여기에 적용되지 않는다. (CLAUDE.md 5장)
- **비멱등적 시트 쓰기 금지.** Actions 재실행으로 같은 스크립트가 두 번 돌아도 같은 글이 두 번 나가면 안 된다.

> **운영 로그는 남긴다.** 이 스크립트는 무인 실행이라 Actions 로그가 유일한 관측 수단이다.
> 선택한 `id`, 발송 성공/실패, `status` 갱신 결과, 건너뛴 이유는 반드시 로그로 남긴다.
> 금지 대상은 디버깅 잔여물과 자격증명 출력이지 운영 로그가 아니다.

### 대시보드 (도입 시)

- **클라이언트 코드에서 Sheets·Telegram 자격증명에 접근 금지.** 브라우저 번들에 들어가는 순간 유출이다. 구조 취향 문제가 아니라 보안 경계다.
- Google Sheets 클라이언트를 컴포넌트 내부에서 직접 생성 금지 → 전용 모듈(`src/sheets.ts` 등)에서 import.
- `useEffect`로 데이터 페칭 금지 → TanStack Query(React Query) 사용.

**보류 중인 규칙** (스택 확정 후 확정한다.)

- 스타일링 방식 미확정. Tailwind 채택 시 "인라인 스타일 금지 → Tailwind 클래스" 추가.
- 프레임워크 미확정. Next.js 채택 시 "API Route 신규 생성 금지 → Server Action" 추가.
  Vite SPA로 가면 Server Component·Server Action·API Route가 존재하지 않으므로 이 규칙 자체가 성립하지 않는다.

## Claude 코드 작성 지침

LLM의 흔한 코딩 실수를 줄이기 위한 행동 지침.

**트레이드오프:** 이 지침들은 속도보다 신중함을 우선한다. 사소한 작업은 판단해서 적용할 것.

### 1. 코딩 전에 먼저 생각하기

**가정하지 말 것. 혼란을 숨기지 말 것. 트레이드오프를 드러낼 것.**

구현 전에 아래를 확인할 것.

- 가정을 명시적으로 서술한다. 불확실하면 질문한다.
- 여러 해석이 가능하면 제시한다 — 조용히 선택하지 않는다.
- 더 단순한 접근이 있으면 말한다. 필요하면 반론을 제기한다.
- 불분명한 부분이 있으면 멈춘다. 무엇이 혼란스러운지 명시하고 질문한다.

### 2. 단순함 우선

**문제를 해결하는 최소한의 코드. 추측성 코드는 없다.**

- 요청받은 것 이상의 기능은 추가하지 않는다.
- 단일 사용 코드에 추상화하지 않는다.
- 요청하지 않은 "유연성"이나 "설정 가능성"을 추가하지 않는다.
- 불가능한 시나리오에 대한 에러 처리를 하지 않는다.
- 200줄로 작성했는데 50줄로 가능하다면 다시 작성한다.

스스로 물어볼 것. "시니어 엔지니어가 이걸 보고 과하게 복잡하다고 할까?" 그렇다면 단순화한다.

### 3. 외과적 변경

**반드시 필요한 곳만 건드린다. 내가 만든 지저분함만 정리한다.**

기존 코드를 수정할 때.

- 인접한 코드, 주석, 포맷을 "개선"하지 않는다.
- 망가지지 않은 것을 리팩토링하지 않는다.
- 내 스타일과 달라도 기존 스타일을 따른다.
- 관련 없는 dead code를 발견하면 언급은 하되 삭제하지 않는다.

내 변경으로 인해 orphan이 생긴 경우.

- 내 변경으로 인해 사용되지 않게 된 import/변수/함수는 제거한다.
- 기존에 있던 dead code는 요청받지 않으면 건드리지 않는다.

테스트: 변경된 모든 줄은 사용자의 요청으로 직접 추적 가능해야 한다.

### 4. 목표 중심 실행

**성공 기준을 정의한다. 검증될 때까지 반복한다.**

작업을 검증 가능한 목표로 전환할 것.

- "유효성 검사 추가" → "잘못된 입력에 대한 테스트를 작성하고, 통과시킨다"
- "버그 수정" → "버그를 재현하는 테스트를 작성하고, 통과시킨다"
- "X 리팩토링" → "리팩토링 전후 테스트가 통과하는지 확인한다"

여러 단계 작업이라면 간략한 계획을 먼저 서술할 것.

```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

### 5. 한국어 출력 시 문장 끝에 콜론 금지

**한국어 문장은 마침표로 끝낸다. 콜론으로 끝내지 않는다.**

사용자가 한국어로 작성하면 출력도 한국어로 한다.

- 다음 줄이 목록이나 예시여도 문장을 `:`로 끝내지 않는다.
- 코드, key-value 쌍, 레이블 내부의 콜론은 허용된다. 문장 끝에는 금지다.

### 6. 새 파일 상단에 한국어 한 줄 주석

**새 소스 파일을 만들 때 첫 줄에 파일의 역할을 설명하는 한국어 한 줄 주석을 작성한다.**

- TypeScript/JavaScript: `// 사용자 인증 상태를 관리하는 Context Provider`
- 필수 디렉티브(`'use client'`, `'use server'`) 바로 아래에 위치시킨다.
- 설정 파일(`*.config.ts`, `package.json` 등)은 생략한다.

이유: 에이전트는 전체 코드베이스가 아닌 파일 단위로 선택적으로 읽는다. 한 줄짜리 한국어 헤더가 있으면 다음 세션이 전체 파일을 다시 읽지 않아도 즉시 맥락을 파악할 수 있다.

### 7. 계획 + 체크리스트 + 컨텍스트 노트

**사소하지 않은 작업이라면 코딩을 시작하기 전에 세 가지 산출물을 먼저 만든다.**

- **계획** — 무엇을 왜 만드는지.
- **체크리스트** (`checklist.md`) — 체크박스 형태의 구체적인 작업 목록. 진행하면서 체크한다.
- **컨텍스트 노트** (`docs/context-notes.md`) — 작업 중 내린 결정과 그 이유. 지속적으로 추가한다.

### 8. 완료 표시 전에 테스트 실행

**코드를 건드렸다면, "완료"라고 말하기 전에 테스트를 실행한다.**

- `npm test` 또는 최소한 `npm run build`로 컴파일 오류가 없는지 확인한다.
- 테스트가 통과하면 결과를 보고한다. 실패하면 수정하고 다시 실행한다.
- 이 단계는 LLM이 가장 자주 건너뛰는 단계다. 타협 불가로 취급할 것.
- **단, 발송 검증은 프로덕션 채널로 하지 않는다.** 테스트 채널이나 dry-run으로 확인하고, 실채널 발송이 필요하면 사용자에게 먼저 확인받는다. (위 "발송 스크립트" 규칙 참고)

### 9. 시맨틱 커밋

**하나의 논리적 변경이 완료되면 커밋한다. 사용자가 요청할 때까지 기다리지 않는다.**

- 테스트: "이 커밋을 한 문장으로 설명할 수 있는가?" 가능하면 커밋한다.
- 좋은 예: "auth 미들웨어 추가". 나쁜 예: "auth 추가하고 UI도 고치고 버그도 수정" (3개로 분리할 것).

### 10. 에러는 추측하지 말고 읽을 것

**실제 에러/로그 줄을 읽는다. 기억에서 패턴 매칭하지 않는다.**

무언가 실패했을 때.

- 전체 에러 메시지와 스택 트레이스를 읽는다.
- 예상하는 내용이 아닌 실제 로그 출력을 확인한다.
- 원인을 확인하기 전에 "흔한 수정법"을 적용하지 않는다.
- 불분명하면 print/log를 추가해서 상태를 확인한 후 수정한다.

### 11. 질문과 작업 요청이 섞인 메시지

**한 메시지에 질문과 작업 요청이 섞여 있으면, 질문에 먼저 답하고 작업 요청은 진행할지 다시 물어본다.**

- 질문에 대한 답을 가장 먼저 제시한다.
- 답변 후 작업 요청을 바로 실행하지 않고, 진행 여부를 재차 확인한다.
